## 1. Headline findings

1. **The live site is not the synced app.** It is built from `main` (commit `d752cbe`), which predates
   sign-in, sync, the security headers and the build checks. The bundle contains no Supabase URL and
   its CSP blocks all outside connections, so data entered there stays on that one device. (**L**)
2. **Cross-device updates are not instant.** The Realtime subscription the app uses never receives
   events (wrong subscription shape). Sync still works through the 60-second, on-focus and
   on-reconnect syncs. (**T**: `supabase/tests/audit.test.ts`)
3. **Imported bank transfers are double-counted.** A CSV row like "Transfer to savings" becomes an
   expense, and the savings account's statement shows it again as income. (**T**)
4. **Deleting data doesn't erase it from the server.** Deletes are tombstones that keep every column,
   so "Delete all data" leaves descriptions and amounts in the account. (**T**)
5. **One sync code path can delete a local record** when a conflicting server copy can't be read.
   Unlikely today, but it is data loss. (**T**)

The core engine is in good shape: the R10,800 / R2,160 plan, available-to-spend, transfers created in
the app, forecast-vs-actual matching, CSV duplicate detection, RLS isolation and backup/restore are
all covered by passing tests.

## 4. Security, isolation, error handling, recovery

- **Data isolation (T, L):** every table has RLS enabled and forced, 52 owner-only policies, no
  privileges for `anon`, user-scoped foreign keys, forced `user_id` in `sync_push`; cross-user reads,
  writes, deletes and Realtime events are refused in tests. Hosted project: anonymous access denied.
- **Keys (T, L):** only the publishable key is used; the build refuses secret keys; the live bundle
  contains none.
- **Server validation (T):** amounts, signs, enums, transfer balance and foreign keys are enforced
  in Postgres.
- **Local data on shared devices (I):** one IndexedDB per user; sign-out removes it by default.
  Session tokens are in IndexedDB.
- **Error handling (T/I):** offline, session expiry, server rejection and conflicts each have a
  status and message (T). Storage failure shows an error screen (I). F-07 and F-09 are the gaps.
- **Backup/restore readiness (T):** JSON backups (file or copy/paste) round-trip, reject tampered or
  orphaned data, restore twice without duplicates, and propagate to the other device. Backups are
  unencrypted (documented). Not yet rehearsed on the live site, which is the old build.
- **Deletion and retention (T):** F-05 — needs a decision before real data.
